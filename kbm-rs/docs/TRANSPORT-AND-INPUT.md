# 네이티브 전송·입력 코어

2026-11-21 · 구현/검증 기록 · HID 화면/API 이관 완료를 뜻하지 않습니다.

## 전송

`actor.rs`가 허용 관리 VID/PID를 검색하고 MCU별 독립 스레드에서
HELLO/INFO/STATUS로 확인한 세션을 유지합니다. USB 토폴로지 검색은 별도 탐색
스레드에서 수행하여 COM 수신과 500ms 상태 갱신을 막지 않습니다.
다른 MCU와 프로토콜 채널의 요청을 한 응답 대기에 묶지 않습니다.

`transport.rs`는 실제 하드웨어 없이 시험하는 요청 상태 머신입니다.

- 채널0/1/2/4/5는 각1개, STORAGE의 UPLOAD_DATA(0302)는4개가 미응답일 수 있습니다.
  STORAGE의 다른 명령은 앞선 DATA가 전부 확인된 뒤 전송합니다.
- DATA 응답이 순서와 다르게 도착해도 가장 오래된 ACK hole이 닫히기 전에는
  window를 전진시키거나 뒤의 요청을 완료로 전달하지 않습니다.
- 세션·채널·opcode·sequence·예약 필드와 응답 크기를 대조합니다.
  명시적 거부도 번호를 소비하지만 세션/번호 오류5..8은 전체 연결을 종료합니다.
- 응답 시간 초과 시 자동 재송신하지 않습니다. DOWN 실행 여부가 불확실할 수 있습니다.
- 각 채널의 수락 상한32개는 큐뿐 아니라 꺼낸 요청·전송·HID 완료 대기를 포함합니다.
  별도의 제한된 해제 큐8개를 두어 정상 큐가 찼을 때도 정리를 요청할 수 있습니다.
- HID→SYSTEM→SERIAL 우선순위를 사용하되 높은 우선순위8회 뒤에는 준비된
  STORAGE/NETWORK/DEBUG를 순환하여 bulk 기아를 막습니다. 한 프레임 안에는
  다른 프레임을 끼워 넣지 않습니다.
- HID ACK의4B ticket을 수락으로 처리하고 0180 HID_DONE을 별도로 기다립니다.
  ACK보다 먼저 온 DONE도 최대64개 보관하여 처리합니다. 이벤트 중복과 sequence gap을 셉니다.
- 이벤트 구독은256개 유한 broadcast입니다. 향후 TTY/NCM 소비자는 lag와 credit를
  별도로 처리해야 하며, 이를 구현했다는 의미는 아닙니다.

Metadata 범위는 PING/INFO/STATUS/이름 GET만 허용합니다. Cleanup 범위는
원래 UID의 RELEASE_ALL/KEY_UP/BUTTON_UP와 NCM OFF만 허용합니다.
일반 명령은 송신 직전에 활성 UID/세대·소유권 취소·원래 연결 세션을 재검사합니다.

## 입력

`input.rs`의 `InputManager`는 모든 프런트엔드가 함께 사용할 입력 코어입니다.
`NativeBackend`는 위 워커로 실제 HID ticket/DONE을 기다리며, 단위 시험은
기록용 backend를 주입합니다. 자동 시험에서 실제 HID를 발생시키지 않습니다.

- 입력 소유자는 고유 lease ID와 취소 token을 갖습니다. 같은 ID를 새 수명에 재사용하지 않습니다.
- 소유자를 활성 UID/세대뿐 아니라 최초 관리 연결의 프로세스 내 고유 ID와 HELLO
  세션에 한 번만 고정합니다. 같은 UID/세션 번호가 재사용돼도 새 연결로 간주합니다.
  UI FIFO/네이티브 키 캡처 무장/원격 input.open 및 실행 큐 수락 전에 고정하고,
  큐 대기 후와 실제 전송 직전에 다시 검사합니다. 이전 입력을 새 연결로 재해석하지 않습니다.
- 다른 소유자가 키/버튼을 누른 상태에서는 새 소유자의 입력을 섞지 않습니다.
- 유효 usage는4..A4/E0..E7, 일반 키 동시6개, 버튼1..5, 내부 좌표0..32767,
  휠 각축−127..127입니다. 외부 마우스 API는 이 내부 좌표가 아니라 영상 픽셀을 받아야 합니다.
- 중복 DOWN/UP은 `no_op`로 구분합니다. 실제 성공은 `usb_completed`이며
  타깃 OS/앱의 입력 처리를 확인했다는 뜻이 아닙니다.
- 명시적 거부/송신 전 취소와 실행 여부가 불확실한 오류를 구분합니다.
  실행되지 않은 첫 DOWN을 눌린 키로 간주하여 불필요한 해제를 만들지 않습니다.
- 불확실한 DOWN은 반복하지 않습니다. 원래 UID에 RELEASE_ALL을 시도하고,
  이때 BUSY4만 최대5회/20ms 간격으로 다시 시도합니다.
  해제가 확인되지 않아도 후속 사용자 입력과 채널 전환을 영구 차단하지 않습니다.
  실패는 진단/로그에 남기며 실제 성공한 것으로 표시하지 않습니다.
- 키 조합은 단일 입력 트랜잭션으로 DOWN들을 보낸 뒤 UP을 역순으로 시도합니다.
  취소·전환 중에도 UP은 원래 UID로 향합니다. 실패 시 RELEASE_ALL로 복구합니다.
- 채널 전환은 세대 무효화→이전 입력 해제→영상 종료→새 활성 커밋 순서입니다.
  이전 입력 해제 실패는 로그에 남기고 새 채널로 전환합니다.
- 관리 장치 분리 시 기존 UID의 미확인 해제 상태를 보존하고 새 UID에 이전 UP을 보내지 않습니다.
  같은 UID의 새 연결에도 자동 UP/RELEASE_ALL을 보내지 않습니다. 원래 연결에 해제를
  확인할 수 없더라도 새 사용자 입력을 계속 받을 수 있습니다. `hid_recover`는
  요청 시점의 현재 연결을 대상으로 하는 선택적 진단 명령입니다. 복구 요청의 큐 대기 중 연결이 바뀌어도 재지정하지 않습니다.
  종료 시 새 DOWN을 차단하고 기존 입력을 정리한 뒤 COM 워커를 종료/합류합니다.
- 키 값/문자열을 상태나 로그에 직렬화하지 않습니다. 조회 상태는 눌림 개수·해제 불확실 여부만 제공합니다.

## 2026-11-22 · 작업 흐름 유지

사용자 요청으로 해제 미확인 상태를 확인 버튼/복구 버튼으로 풀어야 하는 잠금을
제거했습니다. 원래 MCU에 해제를 한 번 시도하고 실패 결과는 보존하며 전환을
계속합니다. MOVE/WHEEL 완료 누락으로 눌린 키가 있다고 추정하지 않습니다.
미확인 DOWN을 자동 재전송하지 않으며 뒤따른 실제 UP은 원래 연결로 보냅니다.
일반 명령 오류가 특수 키 체크를 해제하지 않습니다. 알림은 4초 뒤 자동으로
사라지고, 다른 화면으로 이동하면 즉시 지워집니다.

같은 날짜 Linux 가상 키보드 추적에서, 현재 눌린 입력이 없어도 과거 해제 실패
이력만으로 RELEASE_ALL을 다시 기다리는 경로가 남아 있었습니다. 새 chord의
사전 정리와 소유자/채널 정리는 실제 보유 입력이 있을 때만 수행합니다. 과거
오류 이력은 새 소유자의 취소 후 정리를 생략하는 조건으로 사용하지 않습니다.
회귀 시험은 이전 실패 → 새 chord DOWN/UP → 후속 입력 취소·해제를 확인합니다.
미확인 DOWN 재전송은 하지 않으며 실제 UP 복구와 원래 연결 검사는 유지합니다.

클릭 후 물리 키 반복은 마우스 HID_DONE을 기다리는 단일 UI 작업자가 키 UP을
약1초 늦추는 경로로 추적됐습니다. UI 작업자는 키보드, 마우스, 정리의 세 유한
대기 흐름을 사용하고 InputManager도 각각의 대기를 분리합니다. 키보드/마우스
안의 명령 순서는 유지하며 마우스 완료가 키 UP이나 포커스 이탈 정리를 막지
않습니다. MCU 티켓은 기존대로 실제 HID_DONE과 대조하며 ACK를 완료로 합성하지
않습니다. 동시 정리로 로컬 눌림 목록이 비워져도 물리 키 UP은 원래 고정된
MCU 세션으로 보냅니다. 늦은 이전 소유자의 마우스 오류는 새 소유자의 키를
해제하거나 보유 상태를 지우지 않습니다.

동봉 FS r63 펌웨어도 각 HID 인터페이스의16개 정적 FIFO와 독립 진행 상태를
사용합니다(총 대기32개). 한 인터페이스의 neutral이 끝나면 그쪽 입력은 다시
진행하지만 RELEASE_ALL 성공 티켓은 양쪽 neutral 완료까지 대기합니다.


추가 입력 API는 [클릭·키 배열 안내](INPUT-SEQUENCES.md)를 따릅니다.
`hid_double_click`과 `hid_key_sequence`를 추가했으며 기존 명령은 유지합니다.
키 배열은 기존 USB 키 opcode로만 전송합니다. 키와 Shift의 DOWN/UP을 같은
최대8명령 묶음에 담아 먼저 요청하고, 실제 HID_DONE을 전부 확인한 뒤 다음
묶음으로 진행합니다. 일반 전송 큐를 함께 사용해 UP의 정리 우선순위가 DOWN을
추월하지 않게 합니다. 실패 정리만 원래 세션의 별도 cleanup 큐를 사용합니다.
